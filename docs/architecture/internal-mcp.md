# Internal provider MCP

T3 Code gives supported provider sessions an authenticated internal MCP server. The server exposes
T3-owned tools that need environment and thread context without asking a provider to supply trusted
filesystem roots or browser-session identifiers.

This MCP surface is separate from user-configured MCP servers. Its credentials are generated by the
T3 server, scoped to one provider session, and passed directly to the provider adapter.

## Endpoints and toolsets

The HTTP server exposes two endpoints:

| Endpoint         | Tools                                                |
| ---------------- | ---------------------------------------------------- |
| `/mcp`           | Collaborative preview tools only                     |
| `/mcp/workspace` | Collaborative preview tools plus `workspace_context` |

The endpoint in a provider's generated MCP configuration determines its maximum toolset. A
credential issued for the preview endpoint cannot be used to obtain workspace tools from
`/mcp/workspace`.

Provider support follows the adapter's MCP transport capability:

| Provider driver                          | Internal MCP transport         | Issued endpoint  |
| ---------------------------------------- | ------------------------------ | ---------------- |
| Codex                                    | Native MCP configuration       | `/mcp/workspace` |
| Claude Agent                             | Per-session MCP configuration  | `/mcp/workspace` |
| Cursor                                   | Per-session MCP configuration  | `/mcp/workspace` |
| OpenCode                                 | Per-session MCP configuration  | `/mcp/workspace` |
| Grok                                     | Preview-only MCP configuration | `/mcp`           |
| Gemini, Hyperagent, and hosted providers | No internal MCP transport      | None             |

This distinction keeps `workspace_context` out of the advertised tool list for unsupported
providers instead of allowing a tool call that can only fail.

## Credentials and authorization

`McpSessionRegistry` issues an opaque bearer token for one environment, thread, provider session,
and provider instance. The registry stores only the token hash. Normal provider stop paths revoke
the credential immediately; a bounded liveness window cleans up sessions that disappear without a
clean stop.

Every request must authenticate before MCP dispatch. Authorization verifies both the credential and
the endpoint capability. The invocation context made available to handlers contains:

- `environmentId`
- `threadId`
- `providerSessionId`
- `providerInstanceId`
- the credential's capabilities and issue time

Neither MCP input nor the provider can choose a workspace root.

## Trusted workspace resolution

`workspace_context` resolves the authenticated thread and its project from the orchestration read
model. The effective root is:

```ts
thread.worktreePath ?? project.workspaceRoot;
```

All returned paths use forward slashes and are relative to that root. Explicit reads reuse the
workspace filesystem service, including its root-containment, symlink, file-kind, binary-file, and
size checks.

## `workspace_context`

`workspace_context` is a read-only batching tool for repository discovery. One call can contain up
to eight independent path/content queries and twelve targeted file reads. Queries support `path`,
`content`, and combined `auto` modes. Reads use one-indexed inclusive line ranges.

Tool annotations declare it read-only, non-destructive, idempotent, and closed-world. It cannot
write files or execute arbitrary commands.

### Deterministic search

Git workspaces use argument-array Git processes without a shell:

- `git ls-files --cached --others --exclude-standard` inventories tracked and untracked paths.
- `git grep -n -I -F --untracked --exclude-standard` searches text content literally.
- Multiword queries with no literal match fall back to identifier tokens and deterministic ranking.
- Combined queries prefer content evidence and de-duplicate matches by path.

Non-Git workspaces use a bounded, one-shot Node filesystem scan. It skips symlinks, binary and
oversized files, dependency/build/cache/VCS directories, environment files, and private-key files.
Useful metadata directories such as `.github` and `.agents` remain discoverable.

The tool deliberately does not use the native file-picker index, persistent watchers, embeddings,
a semantic index, or a background daemon.

### Limits and partial results

Each invocation is bounded by:

- 25,000 inventoried paths
- 200 internal candidates per query
- four concurrent search/read operations
- a two-second search deadline
- 400 lines per explicit read
- 1 MiB per source file
- 64 KiB of returned excerpt and read text

The response-budget builder truncates text before dropping match metadata and marks every affected
child plus the top-level result as truncated. A failure in one query or read is returned alongside
successful siblings when possible. Invalid input, failed authentication, missing thread/project
context, an unavailable root, and path escapes fail the whole tool call.

Local tracing records the selected backend, duration, result counts, and truncation state. Query
strings, file contents, and full filesystem paths are not logged.

## Workspace picker invalidation

The UI file picker keeps its existing native path index. File writes, completed checkpoints, and
checkpoint reverts only invalidate a cached picker index; they do not synchronously rescan it. The
next picker list or search lazily creates a fresh index, keeping mutation and turn-finalization paths
independent from scan latency.
